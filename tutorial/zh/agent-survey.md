# 智能体技术综述

前面二十四章，我们从零开始，一步步搭建了小明的学习助手：

* 大模型 API 和智能体循环（第 1 到 4 章）：调用大模型，统一不同厂商的接口，写出最简单的对话循环；
* 对话和记忆（第 5 到 8 章）：保存对话历史，压缩成摘要，持久化到文件，流式输出；
* 工具调用和 MCP（第 9 到 12 章）：让模型请求工具，自动生成工具说明，连接远程工具服务器；
* RAG（第 13 到 16 章）：向量嵌入、切块和索引、检索增强生成、长期记忆；
* 推理和规划（第 17 到 20 章）：思维链和 ReAct、推理模型、计划-执行、反思；
* 多智能体（第 21 到 24 章）：工作流、子智能体和交接、安全、可靠性。

我们的代码刻意保持简单：每个概念都用最少的代码实现，方便看清它的原理。但是和今天业界真正在用的智能体系统相比，从模型接口到上下文管理，从工具生态到安全和评估，几乎每个环节都有更完整、更复杂的做法。

本章不写代码，而是梳理智能体领域的主流技术和最新进展，建立一张完整的技术地图，标出我们的教程和业界之间的距离。感兴趣的读者可以顺着这张地图继续深入。

> 智能体技术演进非常快，本章内容截至 2026 年 11 月。文中提到的产品、协议和框架，版本和功能都可能已经变化，使用前请以官方文档为准。

## 技术对比

先用一张表，比较一下我们的学习助手和业界主流的智能体系统：

| 环节    | 我们的学习助手                    | 业界主流做法                                               |

| 模型接口  | OpenAI Chat Completions、Claude Messages，自己封装 `LLMProvider` | OpenAI 推荐新项目使用 Responses API；各家接口逐渐向“条目”（Item）模型靠拢 |
| 智能体循环 | 自己写的 `while` 循环，`max_steps` 限制步数 | 智能体 SDK 和框架：Claude Agent SDK、OpenAI Agents SDK、Google ADK、LangGraph 等 |

| 工具    | `@tool` 装饰器，`ToolRegistry`  | 同样的思路，用 Pydantic 等生成更完整的 Schema；厂商托管的工具（搜索、代码执行、电脑操作） |

| 长期记忆  | 提取事实，存成向量，按相似度召回            | 文件式记忆（`CLAUDE.md`、`AGENTS.md`、记忆工具）为主，配合检索               |

## 模型接口

### 从“消息”到“条目”

我们在第 1 到 4 章使用的 Chat Completions 接口，是以**消息**（Message）为中心的：输入是一个消息列表，输出是一条消息。工具调用、工具结果都被塞进消息的不同字段里。

这种设计来自“聊天机器人”时代。到了智能体时代，一次调用里可能发生很多事情：思考、调用工具、得到结果、再思考、再输出。OpenAI 因此推出了 **Responses API**：输入和输出都是一组类型各异的**条目**（Item），消息只是其中一种，此外还有推理（reasoning）、函数调用（function_call）、函数调用结果（function_call_output）等类型。OpenAI 目前推荐所有新项目使用 Responses API，Chat Completions 继续保留，但新功能会优先出现在 Responses 上。

这对我们的代码有一个直接的影响：从 GPT-5.4 开始，Chat Completions 不再支持在 `reasoning_effort` 不为 `none` 的情况下调用工具。也就是说，第 18 章的 `OpenAIProvider(effort="high")` 只能用于不带工具的调用；如果想让 OpenAI 的推理模型一边思考一边调用工具，就需要改用 Responses API。Responses API 还能在多轮对话之间保留推理内容（可以加密后由客户端保存），这和第 18 章里 Claude 要求原样传回思考块，是同一个思路。

Claude 的 Messages API 本身就是以**内容块**（content block）为中心的：文字、思考、工具调用、工具结果都是不同类型的块，所以它天然适合智能体场景。

### 统一接口

我们自己写了 `LLMProvider`，把 OpenAI 和 Claude 统一起来。业界也有同样的需求：

* 多模型网关和 SDK，把几十家厂商的接口统一成一种格式；
* 一些厂商和社区在推动开放的接口规范，例如基于 Responses 风格的 Open Responses 规范，试图让推理、工具调用等条目在不同厂商之间通用。

各家模型的能力差异（思考块、缓存、托管工具）很难被完全抹平，所以统一接口通常只覆盖“最大公约数”，高级功能仍然需要针对具体厂商来写。我们的 `ClaudeProvider` 必须专门处理思考块，就是一个例子。

## 智能体框架

### 智能体 SDK

我们的 `Agent` 类大约一百行，实现了智能体最核心的循环：调用模型，执行工具，把结果发回，直到模型给出最终答案。

真实的项目通常不会从零写这个循环，而是使用现成的框架。2026 年常见的选择包括：

* **厂商 SDK**：Anthropic 的 Claude Agent SDK、OpenAI 的 Agents SDK、Google 的 ADK（Agent Development Kit）。它们和自家模型结合紧密，提供工具、子智能体、交接、护栏（guardrail）、会话管理等基本组件；
* **通用框架**：LangGraph（用图来描述有状态的工作流）、CrewAI（按角色组织多智能体）、Pydantic AI（强调类型安全）、Microsoft Agent Framework、Mastra 和 Vercel AI SDK（TypeScript 生态）等。

这些框架的核心，仍然是我们在第 4、10、11 章写过的那几样东西：消息、工具、循环。读完本书再去看它们的文档，会发现大部分概念都能一一对应。

### 智能体运行框架

更进一步，像 Claude Code、OpenAI Codex 这样的编码智能体，本身就是一个完整的**运行框架**（harness）：它提供文件读写、命令执行、搜索、权限控制、上下文压缩、子智能体等一整套能力，模型只需要专注于“决定下一步做什么”。Claude Agent SDK 就是把 Claude Code 的这套运行框架开放出来，让开发者用来构建自己的智能体。

一个值得注意的趋势是：越来越多的智能体不再只是调用专门写好的工具函数，而是直接获得一台“电脑”：一个能运行命令、读写文件的沙盒环境。很多原本需要专门写工具的事情，交给模型写一段脚本、跑一条命令就能完成。

### 异步和流式

为了简单，我们的代码全部是同步的，第 8 章之后也不再使用流式输出，并行只在第 21 章用线程实现。真实的智能体系统几乎都是**异步**的：同时处理很多用户、同时调用多个工具、在模型生成的同时把内容流式地推送给界面。长时间运行的任务通常放在后台，通过任务编号查询进度，而不是让用户一直等着。

## 上下文工程

### 从提示词工程到上下文工程

本书前半部分花了不少篇幅在“写好提示词”上：系统消息、工具描述、RAG 提示词、规划提示词。到了智能体时代，业界更多地谈论**上下文工程**（Context Engineering）：智能体在循环中运行，每一轮都会积累更多的内容（工具结果、中间推理、子智能体的回报），问题不再只是“提示词怎么写”，而是“每一次调用时，应该让模型看到哪些内容”。

上下文窗口虽然越来越大（主流模型已经达到数十万到上百万词元），但并不是越长越好。研究发现，随着上下文变长，模型准确回忆其中信息的能力会下降，这种现象被称为**上下文腐化**（Context Rot）。所以上下文被看作一种有限的“注意力预算”，需要精心管理。

### 常用技术

* **压缩**（Compaction）：我们在第 6 章实现的“历史过长时压缩成摘要”，就是最基本的压缩。现在主要厂商都在 API 层面提供了服务端压缩，达到设定的阈值时自动把较早的对话替换成摘要；
* **清理工具结果**：旧的工具返回结果（比如读过的大文件）往往是上下文里最占地方的部分，可以只清理它们，保留对话主线；
* **提示缓存**（Prompt Caching）：智能体每一轮都会重新发送前面的全部内容。如果这些前缀保持不变，就可以被服务器缓存，缓存命中的输入词元价格只有正常价格的一小部分（Claude 上约为十分之一），速度也更快。为了命中缓存，上下文要尽量“只追加、不修改”，系统消息和工具列表要保持稳定。有实践发现，在有缓存的情况下，保留完整历史有时反而比频繁压缩更便宜、效果更好；
* **子智能体隔离**：第 22 章的子智能体就是一种上下文工程。繁杂的细节留在子智能体自己的上下文里，主智能体只看到结论；
* **按需加载**：不要一开始就把所有资料塞进上下文，而是给模型一份“目录”，需要时再去读取具体内容。下面要讲的 Agent Skills 就是这种思路。

### 长时间运行的智能体

前沿的编码智能体已经可以连续工作数小时甚至更久。任务长到一个上下文窗口装不下时，常见的做法是像人类工程师交接班一样：让智能体在工作中维护**进度文件**、待办清单和版本控制记录，新的会话开始时先读这些文件，了解之前做到了哪里，再继续往下做。这可以看作第 7 章持久化和第 19 章计划-执行的升级版。

## 工具

### 工具定义

第 11 章的 `@tool` 装饰器，用 `inspect` 和类型标注自动生成 JSON Schema。业界的框架做的是同样的事情，只是通常借助 Pydantic 这样的库，支持嵌套对象、枚举、默认值、取值范围等更完整的 Schema，并在执行前校验参数。

工具设计本身也越来越受重视。一些经验：

* 工具数量不宜过多，功能不要重叠，否则模型容易选错；
* 工具的名字、描述和错误信息都是写给模型看的提示词（第 11 章）；
* 返回结果要精简，不要把无关的内容一股脑塞回上下文；
* 与其提供几十个细碎的工具，有时不如提供一个代码执行环境，让模型自己写代码组合调用。

### 托管工具

除了自己写的工具，各家厂商还提供了**托管工具**（Hosted Tools），在厂商的服务器上执行：网页搜索、网页抓取、代码执行、文件检索，以及**电脑操作**（Computer Use）：模型通过截图看到屏幕，再控制鼠标和键盘，像人一样操作图形界面的软件和浏览器。

### Agent Skills

**Agent Skills**（技能）是 2025 年底兴起的一种扩展智能体能力的方式。一个技能就是一个文件夹，里面有一个 `SKILL.md` 文件（包含名称、描述和详细的操作说明），还可以附带脚本、模板和参考资料。

它的关键设计是**渐进式披露**（Progressive Disclosure）：智能体启动时，只读取每个技能的名称和描述；当任务和某个技能相关时，才去读取完整的说明和附带的文件。这样，智能体可以“学会”很多种专门的操作流程，又不会让上下文膨胀。

Anthropic 在 2025 年 10 月推出这种格式，同年 12 月把它发布为开放标准。到 2026 年，它已经被几十个智能体产品和编码工具支持。

技能和 MCP 是互补的：MCP 提供“能做什么”（连接外部系统的工具），技能提供“怎么做”（完成某类任务的经验和流程）。

## MCP 和智能体协议

### MCP 的演进

第 12 章，我们用 MCP 连接了远程的 DeepWiki 服务器。MCP 由 Anthropic 在 2024 年底提出，此后迅速成为智能体连接外部工具的事实标准，OpenAI、Google、微软等也都支持它。

2025 年 12 月，Anthropic 把 MCP 捐赠给了 Linux 基金会旗下新成立的**智能体 AI 基金会**（Agentic AI Foundation，AAIF），由多家公司共同管理。AAIF 的创始项目还包括 Block 的 goose 智能体框架和 OpenAI 提出的 `AGENTS.md` 约定（一个告诉编码智能体项目规则的说明文件）。

2026 年，MCP 规范经历了自发布以来最大的一次修订：

* **无状态架构**：服务器可以像普通的 HTTP 服务一样部署在负载均衡后面，更容易扩展。我们在第 12 章里写的 `MCPConnection` 需要维持一个长期连接，这是早期规范的特点，书中关于“先握手、再发现工具”的描述，在新规范下也可能有所变化；
* **授权**：和 OAuth 2.0、OpenID Connect 的实际用法对齐，企业可以用自己的身份系统统一管理智能体能访问哪些 MCP 服务器；
* **长任务**（Tasks）：服务器可以先返回一个任务编号，客户端稍后再查询结果，适合耗时很长的操作；
* **交互界面**（MCP Apps）：服务器不只能返回文字，还能提供可交互的界面；
* **弃用政策**：功能被宣布弃用后，至少保留十二个月才会移除，给开发者留出迁移时间。

### A2A 协议

MCP 解决的是“智能体怎样使用工具”。**A2A**（Agent2Agent）协议解决的是“智能体怎样和另一个智能体合作”，尤其是不同公司、不同框架开发的智能体之间：每个智能体发布一张“名片”（Agent Card），说明自己能做什么；其他智能体可以发现它、给它派发任务、跟踪任务状态、接收结果。

A2A 由 Google 在 2025 年提出，后来也交给了 Linux 基金会管理，并发布了 1.0 版。到 2026 年 4 月，已有一百五十多家机构支持它，主要的云平台也已经集成。

第 22 章的 `agent_as_tool` 和交接，是在同一个程序里的多智能体合作；A2A 则把这种合作扩展到了网络上，跨越不同的系统和组织。不过，在一个团队内部、同一个框架里，多数场景用简单的子智能体就够了，A2A 更适合跨系统的集成。

## 检索

### 混合检索和重排

第 13 到 15 章，我们用余弦相似度在一个 NumPy 数组里做语义检索。生产环境中的检索系统通常更复杂：

* **向量数据库**：Chroma、FAISS、pgvector、Milvus、turbopuffer 等，用近似最近邻（ANN）算法在海量向量中快速查找；
* **混合检索**：向量检索擅长理解意思，但对专有名词、编号、代码标识符这类需要精确匹配的内容不够敏感。所以通常同时做关键词检索（例如 BM25），再把两种结果合并；
* **重排**（Reranking）：先用较快的方法召回几十个候选，再用一个更精确的重排模型给它们重新打分，只把最相关的几个交给大模型；
* **查询改写**：用大模型把用户的问题改写成更适合检索的形式，或者拆成多个子问题分别检索；
* **元数据过滤和权限控制**：企业知识库中，不同的人能看到的文档不同，检索时必须按权限过滤。

### 智能体搜索

第 15 章我们把检索做成了一个工具，让模型自己决定什么时候查、查什么，这种做法叫 Agentic RAG。它在 2025 到 2026 年变得非常普遍，在编码智能体中尤为明显。

Claude Code 的早期版本使用过“向量数据库 + RAG”来检索代码，但团队很快发现，让智能体自己用 grep、glob、读文件等工具去搜索，效果通常更好。原因在于：代码里的很多线索（函数名、报错信息、配置项）需要精确匹配；代码随时在变，预先建好的索引容易过时；而强大的模型已经能像程序员一样，一步步缩小搜索范围。

这并不意味着向量检索过时了。对于大量的自然语言文档、需要按意思而不是按字面查找的场景，语义检索依然很有价值。目前的趋势是两者结合：以智能体搜索为主干，在需要的地方配合语义索引。

## 记忆

### 文件式记忆

第 16 章，我们把关于小明的事实提取出来，存成向量，按相似度召回。这是一种经典的长期记忆设计，Mem0、Zep、Letta 等记忆框架都提供了类似的功能，有的还会把记忆组织成知识图谱，处理事实的更新和冲突。

不过，2025 到 2026 年的一个明显趋势是**文件式记忆**：记忆就是普通的文本文件，由智能体自己读写和整理。

* 编码智能体会读取项目里的说明文件（`CLAUDE.md`、`AGENTS.md`），了解项目的规则和约定；Claude Code 还会在工作中自动把学到的东西记到本地的记忆文件里；
* Claude 的 API 提供了记忆工具（Memory Tool），让模型在一个由开发者托管的目录里创建、读取、修改记忆文件；
* ChatGPT、Claude、Gemini 等聊天产品也都有了跨对话的记忆功能，通常是把一份简短的用户档案直接放进上下文，再对更久远的历史做检索。

文件式记忆的好处是简单、透明：用户可以直接打开文件，看到智能体记住了什么，也能手动修改或删除。这正好回应了第 16 章提到的两个问题：事实会过时，以及隐私。

### 记忆的难点

无论用哪种方式，长期记忆都面临同样的难题：记什么、不记什么；新旧事实冲突时怎么处理（“我在北京”和“我搬去上海了”）；记忆越来越多以后怎样整理和遗忘；以及怎样让用户看得到、改得了、删得掉。这些仍然是活跃的研究和产品方向。

## 推理和规划

### 推理模型

第 18 章的推理模型，在 2026 年已经是主流。几个变化值得一提：

* **交错思考**：模型可以在两次工具调用之间继续思考，根据工具结果调整计划，而不是只在开始时想一次；
* **推理内容的保留**：Claude 要求在工具调用过程中原样传回思考块；OpenAI 的 Responses API 也可以跨轮次保留（加密的）推理内容。保留推理能让模型在多步任务中保持思路连贯；
* **自适应思考**：模型根据问题的难度自己决定想多少，开发者用 `effort` 之类的参数控制大致的投入，在质量、速度和费用之间权衡。

推理能力的提升，也让一些过去必须靠外部流程实现的东西，被模型“内化”了。第 17 章的思维链提示、第 19 章的部分规划工作，现在很多时候模型自己在思考中就完成了。

### 规划和自我验证

第 19 章的计划-执行，在产品中常常表现为**待办清单**：智能体先列出要做的事，然后一项项完成并打勾，中途发现新情况就更新清单。用户可以随时看到进度，也可以在开始前修改计划。

第 20 章的反思，在编码智能体中最常见的形式是**用测试来验证**：写完代码后运行测试，失败了就读错误信息、修改、再运行。这正是第 20 章“能用代码检查的，就用代码检查”的原则：测试是最可靠的评估器。

## 多智能体

第 22 章介绍的子智能体、智能体对话和交接，是目前多智能体系统最常用的三种模式，主流的智能体 SDK 都直接提供了对应的组件。

实践中的几点经验：

* **适合拆分的任务**：可以并行、彼此独立的工作（比如同时调研多个方向），用多个子智能体效果很好，Anthropic 的多智能体研究系统就是一个例子；
* **代价**：多智能体会成倍增加词元消耗，子智能体之间也容易因为信息不全而做出互相矛盾的决定。需要紧密协作、共享大量上下文的任务（比如修改同一份代码），往往还是单个智能体更可靠；
* **先简单，后复杂**：第 21 章的原则依然适用，能用工作流解决的，就不要用智能体；能用一个智能体解决的，就不要用多个。

## 安全

### 提示词注入

第 23 章演示了间接提示词注入：网页里藏着给 AI 看的指令。到 2026 年，这仍然是智能体面临的头号安全问题。在 OWASP 的大模型应用十大风险中，提示词注入仍排第一；OWASP 在 2025 年 12 月又专门发布了**智能体应用十大风险**，把“通过注入劫持智能体的目标”列为首要风险。

在聊天机器人里，提示词注入的后果是一个错误的回答；在智能体里，后果是一个错误的**行动**。而且研究表明，针对现有防御的自适应攻击，成功率仍然很高。所以业界普遍认为，不能指望靠模型“识破”所有攻击，而是要从系统设计上限制被攻破之后的损失。

### 纵深防御

第 23 章的人工确认、最小权限、输入输出检查，在业界都有更完整的版本：

* **沙盒**：智能体在隔离的环境（容器、虚拟机）中运行命令，限制它能访问的文件和网络。就算被劫持，也碰不到沙盒之外的东西；
* **细粒度权限**：区分只读和写入操作，哪些命令可以直接执行、哪些需要确认、哪些禁止，都可以配置。权限只授予当前任务需要的部分；
* **按设计隔离不可信数据**：例如 CaMeL 这类研究方案，把“理解用户意图、制定计划”和“处理不可信的外部数据”分开，并跟踪每个数据的来源，不让来自网页的内容影响控制流程；
* **供应链安全**：MCP 服务器和技能都是第三方代码和说明，安装前要审查，就像安装软件包一样小心；
* **审计**：记录智能体的每一个动作，事后可以追查。

## 可靠性和可观测性

### 链路追踪

第 24 章，我们用 `note` 打印每次调用的耗时和词元数。真实系统需要的是**链路追踪**（Tracing）：把一次用户请求中的每一步（每次模型调用、每次工具调用、每次检索、每个子智能体）记录成一个“跨度”（Span），组织成一棵树。出了问题时，可以看到到底是哪一步慢了、错了、花钱多了。

OpenTelemetry 已经为生成式 AI 定义了一套语义约定（GenAI Semantic Conventions），统一了模型名称、词元用量等字段的命名。Langfuse、Arize Phoenix、LangSmith 等工具可以收集和展示这些数据。

### 费用和限流

智能体的费用比普通的聊天高得多：一个任务可能调用模型几十次，每次都带着越来越长的上下文。常见的做法包括：设置每个任务、每个用户的预算上限（第 24 章的动手试试）；用提示缓存降低重复输入的费用；简单的子任务（分类、路由、摘要）交给更小、更便宜的模型；对用户和任务做限流。

## 评估

### 自建评估

本书一直是“运行一下，看看输出”。这在学习时没有问题，但真实的智能体需要系统的**评估**（Evals）：

* **评估集**：收集一批有代表性的任务和期望的结果，每次修改提示词、更换模型、调整工具后都重新跑一遍，防止“修好一处、弄坏另一处”；
* **代码评分**：能用代码判断对错的（输出格式、测试是否通过、是否调用了正确的工具），就用代码判断；
* **LLM 评审**（LLM-as-a-Judge）：需要理解内容的（回答是否准确、是否有帮助），用另一个大模型按评分标准打分，就像第 20 章的“严格老师”；
* **人工抽查**：定期由人来检查一部分结果，校准自动评估。

智能体的评估比普通问答更难：同一个任务可能有多种正确的完成方式，结果也有随机性，通常需要多次运行取平均。

### 公开基准

业界常用的智能体基准包括：

* **SWE-bench** 系列：给定真实的 GitHub 仓库和问题，让智能体修改代码，通过测试才算完成。早期常用的 SWE-bench Verified 因为数据污染等问题，已被一些厂商停止使用，更难、更抗污染的 SWE-bench Pro 逐渐成为新的参考；
* **Terminal-Bench**：在真实的命令行环境中完成各种任务；
* **OSWorld**：在真实的操作系统中，通过图形界面完成任务，考察电脑操作能力；
* **τ-bench**（tau-bench）：模拟客服等场景，考察智能体在多轮对话中正确使用工具、遵守规则的能力；
* **GAIA**、**BrowseComp**：考察通用助手和网页浏览、信息搜集的能力。

需要注意的是，基准分数越来越受到质疑：有研究者构造出一个“作弊”智能体，不真正解决任何任务，却在多个主流基准上拿到了接近满分的成绩。同一个模型在不同的运行框架下，分数也可能相差很大。所以，基准分数只能作为参考，最终还要看在自己的任务上的表现。

---

本章，我们梳理了智能体领域的主流技术，可以归纳为几个方向：

* **接口**：从消息到条目，推理和工具调用交织（Responses API、内容块、推理保留）；
* **框架**：从自己写循环到使用 SDK 和运行框架，智能体越来越像拥有一台电脑的“数字员工”；
* **上下文**：从提示词工程到上下文工程（压缩、缓存、子智能体、按需加载、技能）；
* **生态**：从各自集成到开放标准（MCP、A2A、Agent Skills、`AGENTS.md`）；
* **知识和记忆**：从向量检索到混合检索和智能体搜索，从向量记忆到文件式记忆；
* **安全和可靠**：从提示词提醒到沙盒、权限和纵深防御，从打印日志到链路追踪和系统评估。

这些技术看起来纷繁复杂，但它们的骨架，仍然是我们在这本书里亲手搭建的几样东西：**消息、大模型、工具、记忆、循环**。业界的种种进展，大多是在这个骨架上，把每个部件做得更强、更稳、更安全。理解了骨架，再去学习任何一个框架或产品，都会容易得多。
